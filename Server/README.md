# Application server directory

## Архитектура системы

Система построена по принципу клиент‑серверной архитектуры с четким разделением ответственности между слоями.

### Слой доступа к данным (Repository)

Слой репозиториев отвечает за взаимодействие с внешними источниками данных и базой данных:

- **Работа с БД** - выполнение CRUD‑операций через Entity Framework Core.
- **Интеграция с внешними API** - запросы к сторонним сервисам (например, справочники, внешние реестры).
- **Абстракция источников данных** - изоляция бизнес‑логики от деталей хранения и получения данных.

### Слой бизнес‑логики (Service)

Сервисный слой реализует основную бизнес‑логику приложения:

- **Обработка правил валидации** - проверка корректности данных перед сохранением.
- **Координация операций** - управление последовательностью вызовов репозиториев и внешних сервисов.
- **Применение бизнес‑правил** - например, автоматическое сопоставление заявок с существующими студентами, расчет статусов, формирование групп по критериям.
- **Обработка исключений** - централизованная обработка ошибок и формирование понятных сообщений для клиента.

### Слой обработки запросов (Controller)

Контроллеры отвечают за прием и маршрутизацию HTTP‑запросов:

- **Валидация входных данных** - проверка формата и обязательности параметров запроса.
- **Маршрутизация** - определение нужного сервиса для обработки запроса.
- **Формирование ответа** - возврат данных в формате JSON, обработка кодов состояния HTTP.
- **Аутентификация и авторизация** - проверка прав доступа к запрашиваемым ресурсам.

## Функциональные модули - в разработке

- **Модуль заявок:** прием, обработка, валидация и автоматическое сопоставление заявок с существующими записями.
- **Модуль студентов:** ведение личных дел, управление группами, отслеживание прогресса обучения, формирование приказов.
- **Модуль отчетности:** экспорт данных в Excel, формирование отчетов для ФРДО и Росстата, аналитические инструменты.

## Запуск в локальной среде

### Предварительные требования

- **.NET SDK** (версия, указанная в `global.json` или `csproj`).
- **PostgreSQL** (сервер и клиентские утилиты).
- **pgAdmin** (или другой GUI‑клиент для управления БД).
- **Node.js** (для сборки фронтенда).

1. Откройте pgAdmin и подключитесь к серверу PostgreSQL.
2. Создайте новую базу данных, которая будет соответсвовать следующей строку подключения: ```JSON Host=localhost;Port=5432;Database=Cifralabs_local;Username=postgres;Password=123;```.

### Шаг 3. Применение миграций

Для корректной работы приложения необходимо применить все миграции к созданной базе данных.

#### 1. Если база данных новая (пустая)

В терминале в папке проекта (где находится файл `.csproj`) выполните:

```bash
dotnet ef database update --context <ИмяВашегоКонтекста>
```

**Примечание:** Замените `<ИмяВашегоКонтекста>` на реальное имя класса вашего контекста.

#### 2. Если вы вносите изменения в модель данных

1. **Создайте новую миграцию:**
```bash
dotnet ef migrations add <НазваниеИзменения> --context <ИмяВашегоКонтекста>
```

2. **Примените миграцию к базе данных:**
```bash
dotnet ef database update --context <ИмяВашегоКонтекста>
```

---

#### ⚠️ Важное примечание по таблице `__EFMigrationsHistory`

Если вы вручную восстанавливали базу данных из дампа или переносили миграции, убедитесь, что таблица `__EFMigrationsHistory` содержит корректную историю примененных миграций:

* Если таблица пуста, но в проекте уже есть выполненные миграции, EF Core попытается применить их заново, что вызовет ошибки дублирования объектов (таблиц, индексов и т.д.).
* **Решение:** Вручную добавьте в таблицу `__EFMigrationsHistory` строки, соответствующие уже выполненным миграциям, чтобы последней строкой была самая свежая миграция. Это позволит EF Core корректно определить текущее состояние схемы БД и применять только новые изменения.
